# Вывод ДЗ 6+7: от поиска к решению о выпуске

**Решение: кандидат не принят.** `models:/my-qwen-adapter/2` (alias `candidate`) хуже базовой
модели на golden set — общая accuracy 10/51 против 13/51 и критический срез `lang_de`
5/20 против 9/20. Gate отказал, `make promote` отказал, alias `champion` не создан,
baseline не менялся. Отказ по качеству — допустимый итог; ниже — на чём он основан.

Задача: маршрутизация тикетов поддержки из датасета ДЗ 3. Модель — `Qwen/Qwen3-0.6B`,
ревизия `c1899de289a04d12100db370d81485cdf75e47ca`, LoRA, Apple M4 Pro, mps, bf16.
Все runs — коммит `c55bad5` без незакоммиченных правок.

## Часть B. Протокол оценки

Зафиксирован до первой оценки: `evaluation/params.json`, `prep/golden.yaml` и
`prep/behavioral.yaml` вошли в коммит `572f691` раньше первого `make evaluate`.

- **Задача golden:** по тексту тикета выбрать очередь из 10 вариантов или `REFUSE`.
  Ответ — строго `{"answer": "<очередь>"}`; варианты перечислены в input, `expected` в
  prompt не попадает.
- **Набор:** 51 тикет из `test.jsonl` ДЗ 3, 10 очередей, отбор и причины —
  `prep/golden.yaml`, таблица для проверки — `docs/golden-review.md`. Метка — разметка
  датасета; тикет взят, только если текст сам указывает на очередь. Под DVC: стадия
  `eval_data`, `dvc.lock`.
- **Утечка:** индекс всех 28 879 исходных вопросов train собран тем же форматом input;
  точных совпадений и общих `group_id` (тем) — 0. Темы test и train не пересекаются по
  построению split ДЗ 3, там же проверены near-dup пары train/test (Жаккар 0.85).
  Перефразы и переводы между разными темами автоматически не ловятся.
- **Генерация:** одна system-инструкция, greedy (`do_sample=False`), seed 42,
  `max_new_tokens=32`, `enable_thinking=false`, один scorer. `protocol_sha256 ec43e359…`,
  `golden_sha256 daa8bc4e…` одинаковы в обоих отчётах.
- **Критические срезы** (выбраны до оценки):
  - `lang_de` — немецкие тикеты: 1 282 из 3 610 в test, 35% потока; регрессия на них
    незаметна в общей accuracy, если английских больше;
  - `type_incident` — инциденты: ошибка маршрутизации здесь задерживает устранение сбоя,
    а не ответ на вопрос.
  Срезы пересекаются (язык × тип × длина), поэтому в общий n не суммируются.

## Разбор пар ответов

1. **`ccf2220f510b6842`, исправлен.** Платформа упала после обновления McAfee; эталон
   Technical Support, база — IT Support, кандидат — Technical Support. По ROUGE-1
   ответ базы получил бы 0.5 (общее слово «Support»), хотя для маршрутизации это другая
   команда. Сходство слов здесь награждает ошибку.
2. **`9fb0ed977dfbb9b4`, потерян.** Немецкий запрос обновить график обслуживания и
   оповещения о плановых простоях; база верно ответила Service Outages and Maintenance,
   кандидат — IT Support. Судья-модель с рубрикой «ответ разумен» мог бы засчитать IT
   Support: обслуживание похоже на работу IT. Мягкость к соседней метке — типичное
   искажение судьи; точное совпадение метки его не допускает.
3. **`0c711f73638adf72`, потерян.** Тема письма про маркетинговые услуги, а вопрос —
   только об условиях оплаты; эталон Billing, кандидат — Sales and Pre-Sales. Ответ,
   похожий на тему письма, неверен по существу: такие случаи и отмечены в `review`.
4. **`behavior-refusal`.** Просьба написать стих: обе модели назвали очередь, база —
   Product Support, кандидат — Service Outages and Maintenance. Format rate 100% при этом
   не страдает: валидный JSON с неверным решением. Поэтому формат и правильность
   считаются отдельно.
5. **`behavior-format` и `behavior-paraphrase`** — один запрос двумя формулировками. База
   ответила Product Support и REFUSE — ответ зависит от формулировки; кандидат оба раза
   REFUSE — устойчиво, но неверно. Устойчивость к перефразу без правильности ничего не даёт.

**Метрики сходства** (BLEU, ROUGE, BERTScore) считают совпадение слов или близость
эмбеддингов. Для меток они дают частичный балл за неверную очередь с похожим названием
и неполный балл верной очереди, записанной иначе («Billing & Payments»); правильность
метки проверяет только точное сравнение со справочником `choices`.

**Судья-модель** полезен для открытой части нашей задачи — поля `reply` в полном
формате ответа (отвечает ли письмо на вопрос клиента, вежливо ли, нет ли выдуманных
обещаний). Риски: предпочтение позиции A/B, длинных ответов и своего стиля, мягкость к
соседним меткам. Если его добавлять — скрывать имена версий, прогонять A/B и B/A,
хранить рубрику и вердикты и сверять спорные случаи с человеком. Метки он не заменяет.

## Почему кандидат хуже и что дальше

1. **Формат обучения не совпадает с форматом оценки.** Адаптер учился выдавать полный
   JSON (`queue`, `type`, `priority`, `tags`, `reply`) под пятью system-инструкциями ДЗ 3,
   а оценка просит `{"answer": ...}` по другой инструкции. Протокол это допускает, но
   короткое обучение сдвигает модель к другому формату и не учит выбору из `choices`.
2. **Бюджет:** 8 примеров на кандидата. Лучший val loss (−23%) — это выученная форма
   ответа датасета, а не маршрутизация: по accuracy кандидат хуже базы. Loss и качество
   ответов здесь разошлись — отсюда и нужна часть B.
3. **Отказ не обучался:** в датасете нет запросов вне поддержки, поэтому `REFUSE` обе
   модели выдают случайно.

Следующий шаг без подмены baseline: одинаково для всех кандидатов увеличить бюджет,
либо обучать на формате оценки, либо закрепить новый протокол, который разбирает поле
`queue` из ответа в формате обучения (протокол фиксируется до измерения), и добавить в
train примеры отказа. Golden уже использован для решения, поэтому итоговую проверку
следующей версии нужно делать на новом наборе из test.

## Как воспроизвести и где данные

```bash
uv sync --frozen
make data          # dvc repro: импорт split ДЗ 3 -> tokenize -> eval_data
make up && make sweep && make report && make candidate
make evaluate && make eval; make check-negative; make check-storage; make check-all
make reports       # копии metrics/ -> docs/reports/
```

Данные версионирует DVC (`*.jsonl.dvc`, `dvc.lock`), remote — локальный `dvc_remote/`.
Для преподавателя копия набора проверки (51 golden + 3 behavioral) приложена в
`docs/reports/eval-data/`; индекс train (28 879 строк) пересобирается `make data` из
split ДЗ 3 с ревизией `09f8427`.
