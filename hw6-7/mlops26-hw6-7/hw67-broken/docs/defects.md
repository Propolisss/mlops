# Разбор дефектов части A

Четыре заложенных дефекта и пятый, найденный на нашем датасете. Каждый раздел: в чём
состоял, как проявлялся, как исправлен и чем это подтверждается.

**Как сняты числа «до».** Исходный код `hw67-broken` (коммит `e67c90d`, «initial hw6-7»)
запущен на тех же данных и конфиге, но против отдельного MLflow на порту 5007, поднятого
исходным `compose.yaml` (compose-проект `mlops-hw6-broken`, эксперимент `hw6-defects-demo`,
`max_steps: 2`). Основной сервер на 5006 при этом не трогался, демо-стенд после замера
снесён. Вывод замера — `docs/reports/defects-before.txt`.

**Числа «после»** — основной прогон: sweep `b6283f9e8b7e4aa4895f1bd4a2dfb86d` в
эксперименте `hw6-lora`, коммит `c55bad5` без незакоммиченных правок (`git_dirty=False`),
`make check-all`: 9 из 9 проверок MLflow и 24 теста оценки. Отпечаток `tests/`:
`c42ac7788026`, совпадает с выданным — тесты не менялись.

## 1. Шесть кандидатов писались в один run

### В чём состоял

`src/sweep.py` открывал один вложенный run `all-candidates` и в цикле обучал в нём все
шесть конфигураций. Параметры логировались только если у run их ещё нет — то есть только
у первого кандидата; теги и метрики каждого следующего перезаписывали предыдущие.

### Как проявлялся

Исходный код на демо-стенде:

- дочерних runs-кандидатов — **1** (`all-candidates`) вместо 6;
- в params этого run `r=4, lr=0.0001, target_modules=q_proj,v_proj` (первый кандидат),
  а в теге `candidate` — `all-r8-high` (последний): параметры и модель из разных конфигураций;
- в истории `val_loss` **12 точек**, по шесть на шагах 0 и 2 — шесть кривых слиты в одну;
- `metrics/sweep.json` выдаёт шесть строк с одним и тем же `run_id` `773dd32f…`.

Сравнить кандидатов, выбрать лучшего и зарегистрировать именно его модель по такому run нельзя.

### Как исправлен

Цикл открывает свой вложенный run на кандидата: `mlflow.start_run(run_name=candidate["name"],
nested=True)`; параметры логируются в каждом run без условия.

### Чем подтверждается

- В `docs/comparison.csv` 6 строк с **6 разными run_id**, у каждого свои `r`, `lr`,
  `target_modules`, `final_val_loss`.
- Проверка 1 `make check`: «Минимум шесть отдельных законченных runs» — PASS;
  проверка 3 сверяет параметры каждого run с конфигом и находит кривую `val_loss` на шагах 0 и 4 — PASS.

## 2. Артефакты терялись при пересоздании контейнера

### В чём состоял

В `compose.yaml` volume `artifacts` был объявлен, но не подключён к сервису `mlflow`.
Сервер писал файлы в `--artifacts-destination=/mlartifacts` — в слой контейнера.
Postgres с метаданными при этом жил в volume и переживал пересоздание.

### Как проявлялся

`tests/check_storage.py` против исходного compose: после `docker compose up --force-recreate`
в новом контейнере **нет каталога `/mlartifacts`** (`ls: No such file or directory`),
скачивание `persistence/probe.txt` падает с `too many 500 error responses`. Run в базе
остался и ссылается на файл, которого больше нет; то же произошло бы с адаптерами
всех кандидатов и с версиями в реестре.

### Как исправлен

В сервис `mlflow` добавлено `volumes: [artifacts:/mlartifacts]`.

### Чем подтверждается

- `docker inspect mlops-hw6-mlflow-1`: `volume mlops-hw6_artifacts -> /mlartifacts`.
- `make check-storage`: новый контейнер вернул probe-файл с тем же SHA256
  `631c1d3e…14c4ef` (run `bf2f511bbc9441cebd985b1bbefc6113`), `docs/reports/storage-check.json`.
- Проверка 8 `make check` перекачивает этот файл после всех пересозданий и сверяет хеш
  с хешем текущего `compose.yaml` — PASS. Проверка 7 скачивает модель кандидата из того же
  хранилища в новом процессе — PASS.

## 3. В runs не было версий train/val

### В чём состоял

`src/common.provenance()` считает `data_train_sha256` и `data_val_sha256`, но `src/sweep.py`
отбрасывал их: `{k: v for k, v in provenance(p).items() if not k.startswith("data_")}`.

### Как проявлялся

У run исходного кода `data_train_sha256 = None`, `data_val_sha256 = None`. Из MLflow нельзя
понять, на каких тензорах обучен кандидат: после пересборки `data/tokenized` старые runs
выглядели бы актуальными. `src/promote.select()` и проверка 2 сверяют эти теги с текущими
файлами и без них отказывают («отсутствует или устарел data_train_sha256»). На демо
`select` остановился ещё раньше — на числе runs из дефекта 1.

### Как исправлен

`versions = provenance(p)` целиком: теги `data_train_sha256` и `data_val_sha256` пишутся
и в родительский sweep, и в каждого кандидата.

### Чем подтверждается

- Все 6 runs несут `data_train_sha256 = a7441be7…333a8` и `data_val_sha256 = d4c76624…26b62`
  — SHA256 текущих `data/tokenized/train.pt` и `val.pt` (`shasum -a 256` даёт то же),
  а также `git_sha c55bad5…`,
  `code_sha256`, `config_sha256` и `base_revision c1899de2…` (`docs/reports/sweep.json`).
- Проверка 2 «Код, данные, конфиг и база имеют версии» — PASS; `make candidate` прошёл
  `select()`, который сверяет эти хеши с текущими файлами.

## 4. Порог по loss обходился при регистрации

### В чём состоял

В `src/promote.py` функция `gate()` с проверкой `final_val_loss / base_val_loss <= max_ratio`
была написана, но `promote()` её не вызывал: считал отношение, регистрировал версию,
ставил тег `validation=passed` и alias при любом значении.

### Как проявлялся

Исходный `promote()` на демо-стенде с порогом **0.0** для run с отношением **0.807**
зарегистрировал версию 1 модели `hw6-defects-demo`, поставил alias `test` и тег
`validation: passed`. Нулевой порог не может пройти ни один кандидат с положительным loss —
версия в реестре появилась вопреки порогу.

### Как исправлен

`promote()` первым делом вызывает `ratio = gate(run, threshold)`, до `register_model`:
отказ не оставляет в реестре ни версии, ни alias.

### Чем подтверждается

- Проверка 6 `make check` вызывает `promote()` с порогом 0.0 на лучшем run и ждёт
  `ValueError` без регистрации — PASS.
- `make candidate` с порогом 1.0 для `all-r8-high` (отношение 1.6265 / 2.1103 = **0.771**)
  зарегистрировал `my-qwen-adapter` версии 2 с alias `candidate` и тегом `val_ratio=0.771`.
  Версия 1 — кандидат первого поиска до исправления 5, тоже прошла порог (0.747).

## 5. Учебный пул и val состояли из одной темы

Этого дефекта нет в списке задания: он проявляется на данных, упорядоченных по группам,
а наш split ДЗ 3 именно такой.

### В чём состоял

`src/train.py` брал `tr["examples"][:train_limit]` и `va["examples"][:val_limit]` — первые
строки файлов. ДЗ 3 делило данные по темам (`split.group_key: topic`) и записало train и val
сгруппированными по темам, поэтому первые строки — одна тема.

### Как проявлялся

`docs/reports/pools.txt`:

- train-пул 32 — **1 тема, 1 очередь** (Returns and Exchanges / Product), только английский;
- val 8 — **1 тема, 1 очередь** (Technical Support / Account), только английский.

Выбор по loss измерял, как кандидат предсказывает одну тему техподдержки, после обучения
на одной теме возвратов. Первый поиск (`docs/reports/ordered-pools/`) по таким пулам выбрал
`all-r8-high` с отношением 0.747; его версия 1 на golden дала 11/51 и `lang_de` 4/20 против
13/51 и 9/20 у базы.

### Как исправлен

`pool()` в `src/train.py`: `limit` примеров случайной выборкой с `train.seed` (42),
индексы отсортированы. Размеры пулов, бюджет и seed те же, выборка одна для всех шести
кандидатов. Поиск, регистрация и оценка повторены с нуля после коммита.

### Чем подтверждается

- train-пул 32 — **20 тем, 7 очередей**, 23 en / 9 de; val 8 — **8 тем, 6 очередей**,
  5 en / 3 de (`docs/reports/pools.txt`).
- Базовый val loss вырос с 2.0530 до 2.1103: разнородный val труднее одной темы.
  Порядок кандидатов по loss не изменился, лучший — снова `all-r8-high`.
- Проверка 2 сверяет `code_sha256` каждого run с текущим `src/` — PASS: все runs нового
  поиска сделаны исправленным кодом.

- **DVC.** train/val/test ДЗ 3 импортированы `dvc import` с ревизией `09f8427` (md5 совпадают
  с `dvc.lock` ДЗ 3); стадии `tokenize` и `eval_data` в `dvc.yaml`.

  system-инструкцией обучающего набора; `max_new_tokens` 16 → 48.
- **Пробный прогон** sweep на 2 шага шёл в отдельном эксперименте `hw6-smoke`, затем
  эксперимент удалён; в `hw6-lora` только один законченный sweep.
