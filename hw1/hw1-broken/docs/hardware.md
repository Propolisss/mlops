# ДЗ 1 — окружение, инференс и бенчмарк машины

## Конфигурация машины

| Параметр | Значение |
|---|---|
| Компьютер | MacBook Pro |
| Процессор | Apple M4 Pro |
| CPU | 14 ядер: 10 производительных и 4 энергоэффективных |
| Объединённая память | 24 ГБ |
| Устройство инференса | Apple Metal Performance Shaders (`mps:0`) |
| Модель | `Qwen/Qwen3-1.7B` |
| Тип данных | `bfloat16` |

По таблице из первой лекции эта машина относится к профилю **Mac Apple
Silicon, 16 ГБ+**. Для этого профиля рекомендована модель
`Qwen/Qwen3-1.7B`, поэтому она была выбрана вместо базовой
`Qwen/Qwen3-0.6B`. Имя модели задаётся только в `params.yaml` и не
дублируется в Python-коде.

## Первый инференс

Команда `make generate` успешно загрузила модель на устройство `mps:0` и
сгенерировала ответ на промпт из `params.yaml`. Был получен ответ длиной 51
новый токен. Значение `max_new_tokens: 200` задаёт верхнюю границу длины,
поэтому завершение генерации раньше 200 токенов является нормальным.

Замер выполнен командой `make bench`. Перед тремя измерительными запусками
выполнен один прогревочный запуск, результат которого не включался в расчёт
скорости.

| Метрика | Результат |

| Время загрузки модели | 3.34 с |
| Скорость, запуск 1 | 43.76 токена/с |
| Скорость, запуск 2 | 43.85 токена/с |
| Скорость, запуск 3 | 43.86 токена/с |
| Медианная скорость | **43.85 токена/с** |

Модель перед бенчмарком уже была скачана во время первого инференса, поэтому

что после прогрева результат стабилен. Выбранная модель занимает приемлемую
долю от доступных 24 ГБ объединённой памяти и работает с аппаратным ускорением
MPS.

Полный машиночитаемый результат сохранён в `docs/bench.json`.

## Найденные и исправленные дефекты

### 1. Имя модели было захардкожено в коде

**В чём состоял дефект.** Имя `Qwen/Qwen3-0.6B` находилось не только в
`params.yaml`, но и в `src/model.py`, `src/generate.py` и `src/bench.py`.
Таким образом, в проекте было несколько источников одного параметра.

**Как проявлялся.** Изменение `model.name` в `params.yaml` не меняло модель,
которую загружал `load_model()`. Кроме того, название в консольном выводе и
JSON-отчёте могло не соответствовать реально запущенной модели. Проверка с
временной подменой модели на `HuggingFaceTB/SmolLM2-135M-Instruct` завершалась
бы ошибкой.

**Как исправлен.** Во всех трёх местах имя заменено на значение
`params["model"]["name"]`. Теперь единственным источником имени модели является
`params.yaml`, и для смены модели не требуется редактировать код.

### 2. Версии зависимостей не были зафиксированы

**В чём состоял дефект.** В `pyproject.toml` были перечислены только имена
прямых зависимостей без ограничений версий, например `torch` и `transformers`.

**Как проявлялся.** При создании окружения в другое время могли быть выбраны
новые версии библиотек. Это могло изменить поведение программы или привести к
несовместимости, даже если исходный код проекта не менялся.

**Как исправлен.** Для прямых зависимостей указаны точные версии:

```text
torch==2.14.0
transformers==5.16.1
accelerate==1.14.0
numpy==2.5.2
pyyaml==6.0.3
```

После изменения `pyproject.toml` файл `uv.lock` был обновлён. В нём
зафиксировано полное разрешённое дерево прямых и транзитивных зависимостей,
поэтому `uv sync` может воспроизвести использованное окружение.

### 3. Время генерации измерялось вместе с загрузкой модели

**В чём состоял дефект.** Общий таймер запускался до вызова `load_model()` и
использовался для всех измерительных прогонов. Значение времени становилось
накопительным: в него входили загрузка модели и все предыдущие генерации.
Поле `load_time` при этом было жёстко установлено в `0.0`. Прогрев перед
измерениями отсутствовал.

**Как проявлялся.** Рассчитанная скорость `tokens/sec` была занижена и не
описывала скорость одной генерации. Последующие измерения включали всё больше
лишнего времени, а отчёт одновременно показывал нулевое время загрузки.

**Как исправлен.** Для загрузки модели добавлен отдельный таймер. После
загрузки выполняется заданное в `warmup_runs` количество прогревочных запусков.
Каждая измерительная генерация получает собственный новый таймер, а скорость
рассчитывается как отношение числа новых токенов только ко времени этой
генерации. Итоговым показателем остаётся медиана трёх скоростей, устойчивая к
одиночным выбросам.

### 4. Генерация не была воспроизводимой

**В чём состоял дефект.** В конфигурации использовалась температура `0.7`,
которая включала сэмплирование, а готовая функция `set_seed()` нигде не
вызывалась.

**Как проявлялся.** Во время сэмплирования следующий токен выбирается случайно
из распределения вероятностей модели, поэтому два запуска с одним промптом
могли сформировать разные ответы.

**Как исправлен.** Температура в `params.yaml` установлена в `0.0`. При таком
значении код передаёт `do_sample=False` и использует жадную генерацию, каждый
раз выбирая наиболее вероятный токен. Перед загрузкой модели в генераторе и
бенчмарке вызывается `set_seed()` со значением из конфигурации; функция
фиксирует генераторы случайных чисел Python, NumPy и PyTorch.

Самопроверка подтвердила, что два последовательных запуска дают идентичный
вывод.

## Результат самопроверки

Команда `make check` успешно прошла все пять проверок:

1. в `src/` нет захардкоженных имён моделей;
2. модель можно заменить только через `params.yaml`;
3. генерация при `temperature: 0.0` воспроизводима;
4. версии зависимостей и `uv.lock` зафиксированы;
5. загрузка и генерация измеряются отдельно, перед замером есть прогрев.

## Тема датасета

**Классификация русскоязычных обращений в службу поддержки с выводом
результата в формате JSON.** Модель будет получать текст обращения и определять
его категорию и конкретное намерение пользователя (`intent`).

Пример: `«Хочу отменить заказ»` → `{"category":"ORDER","intent":"cancel_order"}`.
