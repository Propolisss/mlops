3. Prefect, результаты и ключ кеша

prepare_input -> acquire_artifact -> evaluate_admission -> publish_version.
Передаются описания с путями, хешами и ID; веса не являются результатами задач.
prepare_input проверяет UTF-8/JSONL, обязательные поля golden, choices/expected,
срезы и уникальные ID. Это реальная проверка 51 строки для процесса оценки.
Её небольшой результат сохраняется в .cache/prepared/<key>.json,
а Prefect хранит сериализованный результат и состояние в .cache/prefect/.

Ключ: SHA-256 канонического JSON {data_sha256, config}. Config включает точную
ревизию токенизатора, хеш шаблона, максимальную длину, версию обработки и SHA-256
реального flow.py. Порядок ключей и путь файла не меняют ключ при одинаковом
содержимом. Байты или параметры обработки меняются — подготовка выполняется снова.
Веса получаются из локального закреплённого артефакта. В flow нет сетевых задач
и автоматических повторов: схема, несовместимость, checksum и quality refusal
завершаются ошибкой. Если добавлять сетевую загрузку, повторять только временные
сетевые ошибки с конечным лимитом; отказ по качеству повторять бессмысленно.

4. Сбой, восстановление, инвалидация и публикация

Команды: make flows и .venv/bin/python tools/evidence.py real-flow.
Каждый flow запускается отдельным subprocess. Журналы содержат имена flow runs,
состояния задач и EXIT_CODE.
  flow-failure.log: подготовка Completed, затем управляемая ошибка, exit 1.
  flow-recovery.log: prepare_input Cached, остальные задачи Completed, exit 0.
  flow-invalidation.log: вход изменён по прежнему пути, PREPARED заново, exit 0.
  flow-repeat.log: повтор выпуска, exit 0; событие фактической публикации одно.
  flow-reject.log: непрошедший отчёт, exit 1; прежний указатель не изменён.
  pointer-failure.log: сбой между указателем и журналом, exit 1.
  pointer-recovery.log и pointer-repeat.log: exit 0, одно событие, pending удалён.
Краткие результаты: flow-summary.json, real-flow-summary.json.

У реальной модели после восстановления кеш используется, кандидат отклонён.
Изменение golden-входа заставляет повторить подготовку, а допуск отказывает:
новые данные требуют нового полного eval. Вход после опыта восстановлен.
SHA-256 accepted.json до и после реальных отказов совпадает:
c2c1f11b1b7ffff5e2dcf2af04bdbfcd8b0c885a530be1983edc61773b30ac9a.

Журнал попыток attempts.jsonl отделён от publications.jsonl. Идентификатор выпуска
хеширует manifest и связанный отчёт, поэтому учитывает модель, runtime и eval.
Один писатель. Перед указателем сохраняется durable intent pending.json.
Запись accepted — временный файл рядом, flush/fsync, os.replace; журнал событий
тоже заменяется атомарно и дедуплицируется по release_id. После сбоя повтор того же
выпуска завершает журнал, даже если указатель уже заменён. Другой выпуск при pending
заблокирован: сначала нужно завершить предыдущий. Это не протокол конкурирующих
писателей и не гарантия восстановления после любой аппаратной потери питания.

5. Gate, manifest и отрицательные проверки

Используется непосредственно quality_gate из evaluation/solution.py ДЗ 6+7.
Перед ним заново считаются score по сохранённым сырым ответам, включая behavioral,
проверяются ID, версии модели, протокол/golden/runtime и хеши исходных файлов.
release-report.json создаётся программой, переносит метрики и отказ gate.
Manifest содержит хеши файлов весов/конфигов/токенизатора; перед публикацией
и загрузкой API реальные файлы перечитываются и сверяются с этим списком.
Токенизатор проверяется также по содержимому backend-tokenizer и special tokens.
Временные файлы не остаются после ошибки замены.

Результат повторного полного eval:
                    baseline          candidate
  accuracy          13/51 (25.49%)    10/51 (19.61%)
  format_rate       51/51 (100%)      51/51 (100%)
  lang_de           9/20 (45%)        5/20 (25%)
  behavioral        0/3               0/3
Gate отказал по accuracy и lang_de; behavioral тоже не позволяет выпустить кандидата.
make gate заканчивается exit 1. Полные отчёты и ответы — docs/evaluation/.
Отказы по incomplete/foreign/reject, NaN/Inf, stale runtime и ошибке диска покрыты
tests/ и integration/. При отказе/ошибке целевой файл побайтно прежний.

Честная baseline: кандидат НЕ получил PASS, champion НЕ назначен. По разделу C
задания обслуживается исходная точка отсчёта из evaluation/baseline.json ДЗ 6+7.
retain-baseline — отдельная однократная инициализация, не обход validate_release.
baseline-reference.json явно содержит quality_gate_passed=false и причину отказа.
Низкая accuracy и 0/3 behavioral у baseline остаются в отчёте: запуск API не означает,
что модель подходит для реальной поддержки клиентов.

7. Настоящий API и перезапуск

FastAPI lifespan запускает фоновую загрузку и прогрев. До завершения ready/generate
возвращают 503; health подтверждает жизнь процесса. Ошибка загрузки оставляет 503.
Версия ответа и runtime_sha256 берутся у backend, уже загруженного в память.
API ограничен localhost, вход до 16384 символов/4096 токенов, тело до 65536 байтов.
Генерация сериализована asyncio.Lock; до вычисления проверяются типы и лимиты.
Для реального runtime разрешён только оценённый max_new_tokens=32.
Ответ: answer, request_id, model_id, runtime_sha256, output_tokens,
generation_seconds, queue_seconds, total_seconds. Это полный JSON, без streaming.

api-smoke.json: реальный ответ {"answer": "IT Support"}, 8 выходных токенов;
пять неправильных/неоценённых лимитов дали HTTP 422 и calls 0 -> 0.
api-input-limits.json: пустой prompt и превышение лимита токенов/символов дали 422,
тело больше 65536 байтов — 413; вызовов генерации не добавилось.
api-restart.json: два независимых процесса действительно загрузили baseline,
оба сначала отдавали ready 503, после прогрева дали одинаковый greedy-ответ.
Второй принятой реальной версии нет: смена и откат отдельно проверены на STUB.
/debug включается флагом --debug для локального опыта; это не публичный production API.

9. Смена A -> B -> A и возврат принятой версии

SystemTests.test_http_loaded_version_restart_and_rollback проверяет настоящий HTTP:
после публикации B работающий backend отвечает A и сообщает A; после перезапуска
ответ и метаданные B; после возврата manifest A и перезапуска снова A.
Фазы STUB_LIFECYCLE и ответы записаны в quick-check.log и linux-tests.log.
Это явно помеченные STUB ONLY версии, не новые обученные модели.
Сбой между указателем и журналом проверяется отдельно в test_safety.py и Prefect.
Для реального отката выбираем ранее принятую версию с прежним полным manifest,
проверяем исходный допуск и файлы, обновляем указатель и перезапускаем API;
до готовности нового процесса трафик не переключаем. Новый runtime требует eval.

10. Ограничения и доступ к артефактам

Маленький golden и короткий sweep из ДЗ 6+7 не доказывают пригодность модели для
настоящего helpdesk. Адаптер обучался другому формату и на восьми примерах.
Один backend, один писатель, нет авторизации внешних клиентов, очереди ограниченной
глубины или автоматического горячего обновления весов. Есть ограничение одновременных
вычислений, но не общей длины очереди. Сервис предназначен для локальной демонстрации.

Prefill обрабатывает весь вход, decode по одному добавляет выходные токены. KV-cache
сохраняет ключи/значения attention и растёт с контекстом и числом обслуживаемых
последовательностей. Здесь не измерялись TTFT/ITL, использование KV-cache, canary,
shadow или SGLang/vLLM. Последовательный Transformers-сервис не демонстрирует paged
KV-cache, continuous batching или prefix reuse специализированных движков.

Веса/venv/кеши/volumes не включены в Git. Baseline публична на Hugging Face по точной
ревизии; tools/restore_baseline.py восстанавливает serving по сохранённым отчётам
без MLflow. Восстановление из HF-кеша проверено: restore-baseline.log.
Для повторной генерации адаптера нужен существующий локальный MLflow либо отдельно
предоставленная папка .real/models/candidate; хеши перечислены в manifest-candidate.
Преподавателю можно передать эту папку отдельно по запросу. Публичного хостинга
адаптера нет, ссылка localhost из отчёта с чужой машины недоступна.
