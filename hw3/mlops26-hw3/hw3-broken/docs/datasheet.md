# Паспорт датасета: маршрутизация обращений в службу поддержки

## Назначение и формат

По письму клиента определить очередь, тип, приоритет и теги обращения и
составить черновик ответа оператора. Выход — один JSON-объект. Это задача
первой линии хелпдеска: куда направить тикет и что ответить, а не установление
технической причины неисправности.

Одна строка JSONL — один обучающий пример:

```json
{"id": "d30615e73296e3ec",
 "topic": "Technical Support / Account",
 "messages": [{"role": "system", "content": "Act as the first line of a helpdesk…"},
              {"role": "user", "content": "Subject:\nAccount Disruption\n\nMessage:\nDear Customer Support Team,…"},
              {"role": "assistant", "content": "{\"queue\": \"Technical Support\", \"type\": \"Incident\", \"priority\": \"high\", \"tags\": [\"Account\", \"Disruption\", \"Outage\", \"IT\", \"Tech Support\"], \"reply\": \"Thank you for reaching out, <name>…\"}"}]}
```

Схема ответа ассистента фиксирована: `queue`, `type`, `priority`, `tags`, `reply`.
Лосс считается только на реплике ассистента, поэтому модель учится и
классификации, и составлению ответа одновременно.

Язык датасета — английский в v1, английский и немецкий в v2.

| Лицензия | **CC BY-NC 4.0** — обязательна атрибуция, коммерческое использование запрещено |
| Что взято | parquet-конвертация всего набора: 61 765 тикетов, языки `en` и `de` |
| Снимок | 20 сентября 2026 года, sha256 `1e2de97c…71a9`, зафиксирован в `sources/manifest.json` |
| Версионирование снимка | DVC, указатель `sources.dvc` |

Использование учебное и некоммерческое, что условиям CC BY-NC 4.0 соответствует.
При любой публикации производного набора атрибуцию нужно сохранить.

Данные **синтетические**: сгенерированы генератором тикетов Open Ticket AI, а не
выгружены из живой системы. Это осознанный компромисс. Реальных размеченных
тикетов поддержки в открытом доступе нет, потому что настоящая переписка
содержит персональные данные клиентов; проверялись `bitext`, MASSIVE,
Twitter Customer Support и русскоязычные наборы DeepPavlov — у одних нет меток,
у других текст состоит из шаблонов с плейсхолдерами `{{Order Number}}`.

Сеть живёт только в `scripts/fetch_source.py`. Стадия `collect` читает уже
скачанный снимок, поэтому `dvc repro` воспроизводим и не зависит от того, что
автор датасета сделает со своим репозиторием завтра.

## Что сделано руками

Готовый чужой набор — сырьё, а не сдача. Источник представляет собой плоскую
таблицу с колонками `subject`, `body`, `answer`, `queue`, `type`, `priority`,
`tag_1…tag_8`, `language`. В обучающий формат он превращён четырьмя действиями,
и каждое видно числом в `metrics/collect.json`.

### 1. Сужение

Параметр `collect.queues` ограничивает набор перечисленными очередями; в сданной
версии он `null`, взяты все десять. Версия датасета выбирает языковые срезы:
v1 — только английский, v2 — английский и немецкий.

### 2. Сверка разметки источника

Чужая разметка не принимается на веру (`collect.verify_labels`):

| Проверка | Отсеяно, v1 | Отсеяно, v2 |
|---|---:|---:|
| Нет обязательного поля (`subject`, `body`, `answer`, `queue`, `type`, `priority`, `tag_1`) | 3 644 | 18 488 |
| `priority` или `type` вне допустимого набора | 0 | 0 |
| Противоречивая разметка: тот же текст под разными метками | 50 | 56 |

Противоречивые тикеты выбрасываются **всеми копиями**, а не сводятся к одной:
неизвестно, какая из двух разметок верна, и выбор наугад внёс бы в обучение
ошибку под видом факта.

### 3. Нормализация текста

Источник выгружен в CSV, и переводы строк в нём остались двумя символами —
обратным слэшем и «n»; часть абзацев размечена тегом `<br>`. Для модели это
мусорные токены посреди предложения. Экранирование развёрнуто в **5 650**
строках v1 и **22 944** строках v2. Плейсхолдеры анонимизации (`<name>`,
`<tel_num>`, `<acc_num>`) сохранены: они несут смысл.

### 4. Обогащение

- **Составная тема.** В источнике темы нет. Ключ группы собран как
  `queue / tag_1`, например `Technical Support / Security`. Одной очереди было
  бы мало: их всего десять, а крупнейшая занимает 28.9% набора при пороге
  `max_group_share: 0.10`. Главный тег дробит очередь на предметные темы и даёт
  **414** групп в v1 и **564** в v2.
- **Инструкция.** В источнике её нет вообще. Написаны пять равнозначных
  формулировок задачи; вариант выбирается детерминированно по sha1 от `id`.
  Единственная формулировка на весь датасет заучивается моделью как константа.
- **JSON-ответ.** Плоские колонки свёрнуты в один объект с пятью полями.
- **Идентификатор.** В источнике его нет, считается как sha1 от языка, темы
  письма и тела. Язык входит в хэш: в многоязычной выгрузке встречаются
  переводы одного тикета, и без него id совпали бы.

## Сплит и контаминация

Сплит идёт **по группам**: тема целиком уезжает в один сплит. Формулировки
внутри одной темы — парафразы друг друга, и построчная раздача разносит их по
train и test. Крупные группы раздаются первыми, иначе последняя большая тема не
влезает в оставшийся зазор и доли разъезжаются.

| | train | val | test |
|---|---:|---:|---:|
| Строк, v1 | 16 696 | 2 087 | 2 087 |
| Доля | 0.80 | 0.10 | 0.10 |
| Тем | 157 | 128 | 129 |

Проверка контаминации — отдельная стадия (`make contamination`, возвращает 1 при
любом пересечении, годится для CI). Пересечения train/test:

| Ключ | Значение |
|---|---:|
| По `id` | 0 |
| По нормализованному тексту | 0 |
| По группам | 0 |
| Near-dup пары, порог 0.85 | 0 |

Порог near-dup в чистке и в проверке контаминации совпадают (0.85). Разные
пороги ловили бы не контаминацию, а разницу порогов.

**Следствие, о котором нужно знать.** Темы в test не встречаются в train, то
есть тест получается zero-shot по темам. Это прямое требование задания
(`group_overlap = 0`), но модель, обученная на таком сплите, на тесте увидит
очереди и теги в незнакомых сочетаниях. Для метрик маршрутизации это строгая, а
не завышенная оценка.

## Гейт разнообразия

**Ни один порог в `params.yaml` не менялся** — значения авторские.

| Порог | Требование | v1 | v2 |
|---|---|---:|---:|
| `min_examples` | ≥ 1000 | 20 870 | 36 099 |
| `min_system_prompts` | ≥ 3 | 5 | 5 |
| `min_groups` | ≥ 50 | 414 | 564 |
| `max_group_share` | ≤ 0.10 | 0.0564 | 0.0576 |
| `min_answer_len_ratio` | ≥ 1.6 | 2.55 | 2.74 |
| `max_same_length_share` | ≤ 0.25 | 0.0033 | 0.0025 |
| `max_duplicate_answer_share` | ≤ 0.30 | 0.0017 | 0.0011 |

Два последних порога проходятся только потому, что в JSON-ответ входит поле
`reply`. Без него задача сводится к чистой классификации, ответ становится
функцией от метки, и его длина зажимается схемой: замер на этих же данных дал
p90/p10 = 1.42 при пороге 1.6 и долю повторов 26.5%. Переключатель оставлен
в `collect.include_reply`; при `false` порог `min_answer_len_ratio` придётся
снижать до 1.4 с обоснованием.

## Персональные данные

Счётчики нулевые: `pii_hits` = 0 по телефонам, почте и датам рождения,
замаскировано 0 строк. Это ноль, полученный проверкой, а не отсутствием
проверки — стадия включена (`clean.pii.enabled: true`) и отрабатывает на каждом
прогоне.

Причина нуля в источнике: он анонимизирован на стороне автора, персональные
данные заменены плейсхолдерами. В английском срезе их 11 296 `<tel_num>`,
6 152 `<name>`, 2 897 `<acc_num>`, 36 `<email>`. Сырых адресов почты в снимке
ноль — проверено регулярным выражением по всему файлу.

Побочное следствие для обучения: модель, обученная на этих данных, будет
воспроизводить плейсхолдеры в ответах. Перед использованием их нужно либо
заменять на реальные подстановки, либо вырезать шаблоном.

## Чего датасет не покрывает и где перекошен

- **Не реальные обращения.** Данные синтетические. Живые клиенты пишут короче,
  грубее и с опечатками; здесь все письма построены по образцу делового
  английского. Модель, обученная на этом, на реальном потоке просядет.
- **Приоритетов три, а не пять.** В источнике их пять, но все 1 914 тикетов
  `critical` и 1 783 `very_low` пришли из старой выгрузки, где нет колонок
  `answer`, `type` и `tag_1`, и целиком отсеяны проверкой обязательных полей.
  Датасет не научит отличать критический инцидент от обычного.
- **Русского языка нет.** v1 английский, v2 плюс немецкий.
- **Длинный хвост тем.** Из 414 тем у 278 меньше десяти примеров. На редких
  темах модель обучится плохо, и метрику по ним считать бессмысленно.
- **Однородный стиль ответов.** `reply` сгенерирован одной моделью, поэтому
  интонация и структура ответов почти не меняются. Разнообразие набора держится
  на темах и длинах, а не на голосе оператора.
- **Лицензия NC.** Коммерческое использование запрещено.
- **Разметка не проверялась человеком.** Сверка ловит отсутствующие поля,
  значения вне набора и противоречия, но не проверяет, что тикет действительно
  относится к назначенной очереди.

## Как воспроизвести

```bash
uv sync
uv run python scripts/fetch_source.py   # снимок источника, ~25 МБ
make repro                              # весь пайплайн
make check                              # восемь проверок
```

Разница между версиями показывается так:

```bash
git commit -am "dataset v1"   # метрики v1 попадают в историю
make v2                       # переключить версию и пересчитать
make diff                     # dvc metrics diff: v1 → v2
```

Данные в git не попадают ни при каких обстоятельствах: `data/` и `sources/`
перечислены в `.gitignore`, версии хранит DVC, remote — папка `dvc_remote/`
рядом с проектом.
