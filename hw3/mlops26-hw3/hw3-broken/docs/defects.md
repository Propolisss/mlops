# Разбор пяти дефектов

Симптомы были описаны в `README.md`, места — нет. Ниже по каждому: в чём
состоял дефект, как проявлялся, как исправлен и каким числом это подтверждается.

Числа приводятся по обеим версиям датасета: **v1** — английский срез,
**v2** — английский и немецкий, именно она лежит в рабочей папке и её показывает
`make check`. Всё воспроизводится командами `make check` и `make contamination`.

---

## 1. Данные уезжали в git

### В чём состоял

Три независимые дыры, каждая из которых по отдельности достаточна, чтобы
датасет оказался в истории git.

- `.gitignore` проекта перечислял `__pycache__/`, `.venv/` и `dvc_remote/`.
  Каталога `data/`, куда пайплайн пишет все артефакты, в нём не было.
- DVC remote не был настроен: `.dvc/config` содержал только
  `[core] autostage = true`. Выгружать данные было некуда, то есть
  единственной копией оставалась рабочая папка.
- В `dvc.yaml` стадия `split` объявляла в `outs` лишь `data/train.jsonl`.
  Файлы `data/val.jsonl` и `data/test.jsonl` не версионировались вообще:
  DVC о них не знал, и `dvc checkout` не смог бы их восстановить.

### Как проявлялся

После `git add . && git commit` в истории оказывались `data/raw.jsonl`,
`data/clean.jsonl`, `data/train.jsonl` и остальные — `git log --stat` показывал
крупные JSONL. Проверка 1 в `make check` падала на трёх пунктах из четырёх.

Цена ошибки: одна версия `data/*.jsonl` весит **88.3 МБ** для v1 и **159 МБ**
для v2. Git хранит каждую версию целиком и ничего не удаляет из истории, поэтому
десять правок датасета дали бы от 883 МБ до 1.6 ГБ, которые `git clone` тянул бы
у каждого следующего человека навсегда.

### Как исправлен

- В `.gitignore` добавлены `data/` и `.cache/`.
- Настроен локальный remote: `dvc remote add -d local dvc_remote`. Каталог
  `dvc_remote/` уже был в `.gitignore`, то есть место под него предполагалось
  с самого начала.
- В `outs` стадии `split` добавлены `data/val.jsonl` и `data/test.jsonl`.
- Снимок источника поставлен под DVC отдельно: `dvc add sources` создал
  указатель `sources.dvc` на 107 байт, а сам каталог на 86 МБ ушёл в кэш.

### Чем подтверждается

```
git ls-files data/ | wc -l   →  0
dvc push                     →  обе версии выгружены
dvc status -c                →  Cache and remote 'local' are in sync
dvc_remote/                  →  333 МБ данных вне git
```

В remote лежат артефакты обеих версий, поэтому `git checkout` на коммит с v1 и
`dvc pull` соберут именно тот датасет, который был на том коммите.

Проверка 1 зелёная целиком: git не отслеживает ни одного файла в `data/`,
`data/` перечислен в `.gitignore`, remote настроен, все пять артефактов из
`params.paths` объявлены в `outs`.

## 2. Смена версии данных не пересчитывала пайплайн

### В чём состоял

Тоже два места, и оба — нарушение правила «стадия пересчитывается по `deps` и
`params`».

- У стадии `collect` в `dvc.yaml` не было секции `params`. Версия датасета
  живёт в `params.yaml` → `collect.version`, файлы-источники лежат на диске
  неподвижно, код стадии не менялся. С точки зрения DVC не изменилось ничего.
- У стадии `clean` в `deps` не был указан `data/raw.jsonl` — выход
  предыдущей стадии. Ребра в графе между `collect` и `clean` не существовало,
  поэтому даже пересчитанный `raw.jsonl` не заставил бы `clean` переисполниться.

### Как проявлялся

`python scripts/set_version.py v2 && dvc repro` сообщал, что пересчитывать
нечего. В `data/` оставались артефакты прошлой версии, метрики показывали
старые числа, и разница между v1 и v2 через `dvc metrics diff` была нулевой —
при том что наборы отличаются почти вдвое.

Это ровно тот случай из лекции, когда утечка не роняет пайплайн и ничего не
пишет в лог: DVC честно отвечает «всё свежо», а данные не те.

### Как исправлен

У стадии `collect` объявлены зависимости и параметры:

```yaml
    deps:
      - sources            # снимок целиком: какие файлы брать, решает params
      - src/collect.py
      - src/textnorm.py
      - src/config.py
    params:
      - collect
      - paths.raw
```

В `deps` стадии `clean` добавлен `data/raw.jsonl`, чем восстановлено ребро
графа. Заодно `metrics/collect.json` объявлен метрикой стадии — без этого
`dvc metrics diff` не показывал бы числа сбора.

### Чем подтверждается

Проверка 4 переключает версию и сравнивает содержимое `data/clean.jsonl`:

```
clean.jsonl пересчитан: v1 (24 567 строк) → v2 (43 221 строк)
```

Контрольные суммы файла до и после переключения различаются, чего и добивались.
`dvc dag` показывает связный граф `collect → clean → diversity/split`.

## 3. Контаминация между train и test

### В чём состоял

`src/split.py` раздавал сплиты **строкам**, а не группам. Функция `row_split()`
перемешивала индексы генератором с фиксированным зерном и резала полученный
список на доли. Группы при этом вычислялись — словарь `sizes` собирал размеры
тем — и никуда не использовались, кроме поля `groups_total` в метриках.

### Как проявлялся

Тикеты одной темы разъезжались по train и test. Формулировки внутри темы —
парафразы друг друга: письмо про сбой доступа к аккаунту написано десятками
способов, но спрашивает об одном и том же и получает ту же разметку.

Утечка не роняла пайплайн и не писала в лог. Единственным её симптомом была бы
подозрительно хорошая метрика на тесте: модель отвечала бы на вопросы, которые
уже видела в обучении под другим номером.

Замер дефектного сплита на очищенных данных v1 (20 870 строк, 414 тем):

| Ключ пересечения | Построчный сплит | Сплит по группам |
|---|---:|---:|
| По `id` | 0 | 0 |
| По нормализованному тексту | 0 | 0 |
| **По группам** | **178** | **0** |
| Near-dup пары, порог 0.85 | 0 | 0 |

Из 190 тем, попавших в test при построчной раздаче, **178 присутствовали и в
train** — протекало 94% тем.

Отдельно стоит отметить, почему пересечения по тексту и near-dup при этом
нулевые: одинаковое уже схлопнуто стадией `clean`. Это иллюстрация тезиса
лекции — ноль получается только после дедупликации, и на уже очищенных данных
утечка видна именно через группы.

### Как исправлен

`row_split()` заменена на `group_split()`: тема целиком уезжает в один сплит.

```python
keys = sorted(groups)
random.Random(seed).shuffle(keys)
keys.sort(key=lambda key: -len(groups[key]))   # крупные группы первыми
...
name = max(filled, key=lambda n: targets[n] - filled[n])
```

Крупные группы раздаются первыми не из эстетики: при случайном порядке
последняя большая тема не влезает в оставшийся зазор, и фактические доли
разъезжаются на проценты. С сортировкой по убыванию размера доли вышли ровно
0.80 / 0.10 / 0.10.

### Чем подтверждается

```
make contamination
  пересечение по id:        0
  пересечение по тексту:    0
  пересечение по группам:   0
  near-dup пар train↔test:  0
контаминации нет
```

Те же нули лежат в `metrics/split.json` в секции `contamination`, то есть стадия
проверяет себя сама, а скрипт остаётся отдельным гейтом для CI. Проверка 5
зелёная.

## 4. Почти-дубли переживали очистку

### В чём состоял

В `src/clean.py` шаг неточной дедупликации был заглушкой:

```python
    # 5. TODO: сюда просится ещё один шаг дедупликации.
    near: set[int] = set()
```

Множество создавалось пустым и сразу уходило в метрики как
`dropped_near_dup: 0`. Функция `near_duplicates()` в `src/dedup.py` была
написана, протестирована параметрами из `params.yaml` — и ни разу не вызывалась.

### Как проявлялся

Точная дедупликация сравнивает нормализованный текст побайтово. Пара примеров,
отличающихся переставленными абзацами, другим отступом или изменённой подписью,
для неё — два разных примера, и оба оставались в датасете.

Проверка 2 подкладывает стадии тот же вопрос, набранный иначе: другие пробелы и
нумерация вариантов через `)` вместо `.`. Точная дедупликация его не видела,
`dropped_near_dup` оставался нулём, и проверка была красной.

### Как исправлен

После точной дедупликации вызывается MinHash + LSH с порогом из `params.yaml`:

```python
    if cfg["near_dup"]["enabled"]:
        nd = cfg["near_dup"]
        near = set(near_duplicates([normalize_text(ex.user) for ex in kept],
                                   shingle_words=nd["shingle_words"],
                                   num_perm=nd["num_perm"],
                                   threshold=nd["threshold"]))
        kept = [ex for i, ex in enumerate(kept) if i not in near]
```

Порядок шагов сохранён: сначала дешёвая точная дедупликация снимает основную
массу, дорогой MinHash работает по остатку. Порог `0.85` тот же, что в
`contamination.threshold` — разные пороги ловили бы не дубли, а разницу порогов.

### Чем подтверждается

На собранном датасете:

| | v1 | v2 |
|---|---:|---:|
| Точных дублей снято | 3 677 | 7 102 |
| Почти-дублей снято | 20 | 20 |

Проверка 2 на подложенном наборе: `dropped_exact_dup = 1`,
`dropped_near_dup = 1` — оба типа повторов пойманы.

Двадцать почти-дублей на фоне 3 677 точных — честная картина для этого
источника: тикеты длинные, и при пороге Жаккара 0.85 на четырёхсловных шинглах
близкими оказываются только действительно переписанные друг с друга письма.
Ноль, который стоял здесь раньше, был не «дублей нет», а «никто не искал».

## 5. Гейт разнообразия был отчётом, а не гейтом

### В чём состоял

`src/diversity.py` считал все семь метрик, честно собирал список нарушенных
порогов — и печатал его как предупреждение:

```python
    if failed:
        # TODO: гейт или отчёт? …
        print("diversity: предупреждение — " + "; ".join(failed))
```

Стадия завершалась с кодом 0. Класс `DiversityError` был объявлен в том же
файле и ни разу не возбуждался.

### Как проявлялся

Вырожденный набор проходил пайплайн целиком. Тысяча строк с одним системным
промптом, одной темой и ответами одной длины проходит и валидацию схемы, и
дедупликацию, и проверку контаминации: строки разные, дублей нет, битого JSON
нет. Формально набор безупречен, а обучение на нём даёт модель, выучившую
шаблон вместо задачи.

Предупреждение в логе `dvc repro` терялось между выводом остальных стадий, и
ничто не мешало такому набору доехать до обучения.

### Как исправлен

Нарушения печатаются по одному на строку, после чего возбуждается
`DiversityError`; на верхнем уровне он превращается в `SystemExit` — без
traceback, потому что стек здесь ничего не добавляет к уже напечатанному
списку.

```python
        print(f"diversity: набор не прошёл гейт, нарушено порогов: {len(failed)}")
        for item in failed:
            print(f"  ✗ {item}")
        raise DiversityError(…)
```

Построчный вывод выбран не случайно: чинить пороги придётся по одному, и
grep по логу должен находить каждое нарушение отдельно.

### Чем подтверждается

Проверка 6 подкладывает стадии вырожденный набор из 1 200 строк. Гейт падает с
ненулевым кодом и печатает **шесть** нарушенных порогов:

```
diversity: набор не прошёл гейт, нарушено порогов: 6
  ✗ системных промптов 1, нужно ≥ 3 — модель заучит единственную формулировку как константу
  ✗ групп 1, нужно ≥ 50
  ✗ крупнейшая группа занимает 100.0% (порог 10%): «одна-единственная тема - 2025»
  ✗ разброс длин ответа p90/p10 = 1.0, нужно ≥ 1.6 — ответы одной длины выдают шаблон
  ✗ 100.0% ответов имеют одну и ту же длину (порог 25%)
  ✗ 99.7% ответов дословно повторяют друг друга (порог 30%)
```

Сама проверка рапортует «назвал 4 нарушенных порога»: `tests/check.sh` считает
строки через `grep -cE` по четырём шаблонам и из шести сообщений распознаёт
четыре. Требование проверки — «≥ 2», так что запас тройной. Число 6 — это то,
что печатает гейт; число 4 — то, что умеет опознать grep.

Проверка 7 подтверждает обратное: на собранном датасете гейт открыт.

| | v1 | v2 (сдаётся) |
|---|---:|---:|
| Строк | 20 870 | 36 099 |
| Системных промптов | 5 | 5 |
| Групп | 414 | 564 |
| Доля крупнейшей группы | 5.6% | 5.8% |
| Разброс длин ответа | 2.55 | 2.74 |

Ни один порог в `params.yaml` при этом не менялся.
